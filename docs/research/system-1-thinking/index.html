The tool call is not the intelligence.

Much of the System-1 excitement points at a real category: applications often need a finite decision, not an essay. A ticket must reach a queue. An alert must be scored. A request must be approved, escalated, or declined.

Jev makes that category visible with three primitives: Choice, Score, and Noul. They select from a defined set, place a state on an ordered scale, or evaluate a yes-or-no statement. The important idea is not that a proprietary model has made software decisions mysterious. It is that the useful output is often structured and small. Jev remains a useful conceptual reference; this paper focuses on the implementation choices available to Origo Labs.

Fastino created the GLiNER2.5 architecture and released GLiNER2.5-Decide as an open-weight specialist for schema-defined decisions. Its release announcement describes the model foundation used by the public gateway.

ZEV: the decision-model layer

ZEV is a closed-weight Origo Labs decision model for finite choices. It scores supplied candidates against shared context in one non-autoregressive forward pass, with candidate order designed not to determine the score. The public product site reports benchmark results for agent routing and Banking77 triage, plus sub-15ms CPU latency under its stated conditions.

ZEV is not a general-purpose agent and does not grant permission to execute. It is the model inside a larger decision system: the surrounding application still owns policy, access, reversibility, and escalation. Licensing, deployment, evaluation, and the forthcoming hosted API are documented at zev-decide.com.

Separate interpretation from authority

The public System-1 Gateway implements this pattern as the application boundary around a local decision model. It turns a message, ticket, alert, or command into a typed interpretation: intent, relevant entities, route, and confidence. A separate policy layer then checks thresholds, approval requirements, supported operations, and idempotency. The model can be ZEV or another local semantic component, depending on the workload.

message → intent + entities → policy → route or action

That boundary is the point. Correct classification does not grant permission to execute. Uncertain or unsupported inputs can abstain; high-risk inputs can escalate; only explicitly allowed, low-risk routes can proceed through an opted-in adapter.

Released implementation

The gateway provides configurable domain packs, entity extraction, accepted/abstained/escalated states, separate execution safety, dry-run idempotent actions, CLI, JSONL, local HTTP, and measurements for latency, throughput, abstention, and calibration. Its recorded Apple Silicon fixture run reports 100% Choice accuracy, 83.3% Score accuracy, and 31.36 ms p99 latency. Those figures apply to the recorded fixture, not a customer deployment or every workload.

Model, policy, and effect are different layers

The System-1 pattern is easiest to reason about when three responsibilities stay separate:

  • Model: score or classify the supplied choices.
  • Policy: decide whether the result is supported, safe, and permitted.
  • Effect: execute through an explicit, idempotent adapter—or escalate.

ZEV occupies the first layer. System-1 Gateway provides the second and third.

Why local is worth testing

For frequent, narrowly defined decisions, local inference can remove a per-request API fee and network dependency while keeping the semantic step within the organization’s boundary. It does not make inference free, eliminate integration work, or establish a universal accuracy claim. Hardware, maintenance, model choice, and the quality of the schema still matter.

Known limits

ZEV expects decision-relevant context and a defined candidate set. None or escalation must be represented explicitly; automatic abstention is not a universal architectural guarantee. Public benchmark results are workload-specific, and thresholds still require evaluation on the domain and hardware that matter to a deployment.

What remains to be proven

The research is not a claim that small models replace general-purpose models for writing, synthesis, research, or planning. It is a narrower question: for a specific operational workflow, can a compact local model and typed policy be accurate enough, abstain safely, and meet the required latency?

Answering it requires a customer-shaped fixture set and reproducible measurements of intent and entity quality, abstention, policy safety, cold and warm latency, and throughput. The prototype provides the contract and evaluation path; each deployment still needs to earn its result.
